# Отчёт: GitHub Actions

## Ответы на контрольные вопросы

**1. Из каких элементов состоит workflow и как они вложены друг в друга?**

Workflow — это один YAML-файл в `.github/workflows/`. Внутри него: событие (`on:`), которое запускает workflow, и один или несколько jobs (`jobs:`). Каждый job выполняется на своём runner (`runs-on:`) и состоит из последовательности шагов (`steps:`). Шаг — это либо shell-команда (`run:`), либо готовый action (`uses:`). Вложенность: workflow → event + jobs → job → runner + steps → step (run / uses).

**2. Чем job отличается от step?**

Job — набор шагов, выполняемых на одной виртуальной машине (runner); разные jobs по умолчанию идут параллельно и на отдельных чистых машинах, файлы между ними не делятся. Step — одна команда или один action внутри job; шаги одного job идут строго по очереди и видят одну и ту же файловую систему.

**3. Чем запуск по push отличается от запуска кнопкой (workflow_dispatch)?**

`push` срабатывает автоматически, когда кто-то отправил коммиты в репозиторий. `workflow_dispatch` добавляет во вкладку Actions кнопку **Run workflow** — workflow запускается вручную, когда человек сам этого захочет, независимо от коммитов.

**4. Как безопасно передать в workflow пароль или токен?**

Через секреты репозитория (Settings → Secrets and variables → Actions) и обращение `${{ secrets.ИМЯ }}`. Значение хранится зашифрованным, не лежит в коде и в логах заменяется на `***`. Писать пароли прямо в YAML или в код нельзя — они попадут в историю git.

**5. Что такое артефакт и зачем он нужен?**

Артефакт — файл (или набор файлов), сохранённый по итогам выполнения job (`actions/upload-artifact`). Нужен, чтобы передать результат между jobs (каждый job работает на отдельной машине) и чтобы потом скачать результат работы (сборку, отчёт, логи) со страницы запуска.

**6. Как заставить один job дождаться завершения другого? Зачем нужен линтер, если есть тесты?**

Ключом `needs: <имя_job>` — тогда job стартует только после успешного завершения указанного.

Линтер нужен, потому что тесты проверяют только то поведение, которое мы заложили в тест, а линтер без запуска кода ищет ошибки и плохой стиль. Пример из лабы: после удаления кавычек (`echo Hello, $1`) тест остался зелёным, потому что вывод не изменился, а `shellcheck` предупредил о неэкранированной переменной, которая сломается, например, при аргументе с пробелом.

**Задание 2 (ошибка).** Первый запуск `manual.yml` завершился ошибкой «Invalid workflow file»: в YAML значение `run: echo "Курс: $COURSE"` содержит двоеточие с пробелом и читается как новый ключ. Исправила, записав команды в блочном стиле (`run: |`).

**Задание 3.** В PR `fix-hello` job `test` был зелёным (вывод не изменился), а `lint` красным: shellcheck сообщил о неэкранированной переменной `$1` (SC2086 — нужны двойные кавычки). После возврата кавычек в ту же ветку проверки перезапустились и обе стали зелёными, PR влит.

**Задание 4.** После удаления `needs: build` jobs `build` и `show` запустились одновременно. Job `show` упал (красный): артефакт `report` ещё не был создан, а скачивать было нечего — jobs идут параллельно на разных машинах. После возврата `needs: build` схема снова build → show и всё зелёное.
